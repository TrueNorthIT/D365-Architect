# Modifying or adding exports/imports

Also read the general `design-principles` skill (language-agnostic engineering practice). This skill holds this repo's own design direction; where they differ, this one wins.

Read `docs/DEVELOPING.md` (architecture) and `docs/yaml-conventions.md` (the audited YAML rules) first; this skill is the working checklist and design direction, not a replacement for them.

## Design direction: minimal YAML in, full-featured XML/metadata out

The YAML is for humans to manage and review. The export therefore aims to be **as small as possible**, while the rebuild (`form build-xml` / `import`) must still emit **everything Dataverse needs for full functionality**.

- **Export omits anything equal to Dataverse's own default.** Example: a FormXML control parameter that is normally `false` is left out of the YAML. On `build-xml`/import, the writer re-adds it (or, where omitting is equivalent, leaves it out) so the resulting FormXML has the full feature set. A missing YAML field always means "left at Dataverse's default", never "unknown" (`yaml-conventions.md` Rule 1).
- **The YAML only has to be reconstructable, not mirror the source format.** Use readable keys (`attributes`, `value`, `xml`), never `@attr`/`#text` sigils (Rule 2).
- **Round-trip is the contract.** Whatever the reader strips, the writer must restore (or prove equivalent). Never trade away import fidelity for a smaller YAML.
- **Only strip once the default is confirmed**, from Microsoft docs, aggregated real samples, or a structural argument — never guessed. Unconfirmed values are captured verbatim (Rule 4). Add helpers to `DefaultValueConventions.cs` rather than inlining ad-hoc checks.
- **Stripping is unsafe for PCF/custom controls without evidence.** Dataverse validates their parameters against the control's own manifest, not the static XSD, so by default `false` values and empty elements under an additional control's `parameters` are preserved (`preserveDefaults`). A control only gets stripped-and-restored defaults after a survey of real exports confirms them, as `ModelFormControlDefaults` did (93 instances, 23 forms, 3 environments — Microsoft documents none of it). Issue #36: dropping them gave a 400 on import or, worse, an accepted import that 502'd `GetClientMetadata`. When unsure, preserve. To survey, aggregate parameters across the raw `*_managed.xml` files in the solution repos.
- **Silent loss is the worst failure.** A write Dataverse accepts but later fails to compile is far harder to diagnose than an import error. Prefer a loud failure or a verbatim capture over a quiet omission.
- **Settle defaults with data now, not incrementally.** When a default is unclear, survey the real exports (all environments, with counts) and document the evidence in the spec, rather than shipping a guess and waiting for the next failure to be reported — that often never happens.
- **Test round trips against verbatim real samples**, including the second pass: rebuilding what was read back must be byte-identical.

## Where things live

| Concern | Location |
|---|---|
| Command (thin Spectre layer) | `D365 Architect/Commands/<Asset>/` — `Export…Command`, `Import…Command`, `…Commands.cs` (registers the branch), wired in `Program.cs` |
| Shared import flow | `Commands/ImportRunner.cs` + `ImportFlowSpec.cs` (diff → confirm → apply); don't re-implement it |
| Export/import services | `Services/Conversion/<Asset>ExportService`, `<Asset>ImportService`, plus `I…` interfaces (`IImportService<TInput,TPreview>`) |
| Source → curated model | `…JsonDefinitionReader` (live Web API); tables also have `EntityXmlDefinitionReader` |
| Curated model | `Services/Conversion/Models/` |
| YAML (de)serializers | `…YamlSerializer` / `…YamlDeserializer` |
| Model → Dataverse | `FormXmlWriter`, `AttributeMetadataJsonBuilder`, `GlobalChoiceMetadataJsonBuilder`, `DataverseClient` (`IDataverseClient`) |
| Default-omission helpers | `DefaultValueConventions.cs` |
| Per-control confirmed defaults | `Services/Conversion/Models/ControlDefaults/` — see below |
| JSON Schema for editors | `schema/*.schema.json` — generated by `YamlSchemaGenerator` from the models |

## Checklist

1. **Model**: add/adjust the property on the curated model. Nullable = optional. Write the XML doc comment as design rationale with evidence; it becomes the schema tooltip (`GenerateDocumentationFile` feeds `YamlSchemaGenerator`).
2. **Reader**: populate it, omitting the default via `DefaultValueConventions` (or a new, confirmed helper).
3. **Writer/builder**: restore it on the way out so import has full functionality. A new field is not done until it is written back.
4. **Diff/preview**: ensure the import diff compares like with like (see `FormImportPreview.ExistingComparableFormXml`) so there are no spurious changes.
5. **Safety**: imports show a diff and require confirmation; never silently delete (`table import` never drops a column; form/view import never create missing records). Route errors through `ErrorConsole` with domain exceptions, never raw stack traces.
6. **New asset type**: add the command branch, register it in `Program.cs`, add the services, reader, writer and (de)serializers, and extend `schema export`.
7. **Tests** (`D365 Architect.Tests`, xUnit): test readers/writers against literal input, and add a **round-trip test** (write → read back, and rebuild twice is byte-identical). Confirm a new regression test fails without your fix. Run `dotnet test "D365 Architect.slnx"`.
8. **Docs & schema**: update `docs/yaml-conventions.md` if you change what absent/omitted means. A `dotnet build` regenerates `schema/*.schema.json`; review and commit that diff.
9. **Never guess a Dataverse API shape**; cite the Microsoft Learn page or live confirmation in the doc comment, or flag that it is unconfirmed.

## Branches and PRs

Branch `feature/jc/{name}` (hotfix: `hotfix/jc/{name}`). Code lives on `develop`; `main` is release. Don't open a PR unless asked.

## Adding confirmed defaults for another control

Per-control defaults are declarative data plus one generic engine, so a new control needs no reader/writer change:

1. **Survey first.** Aggregate the control's `parameters` across every raw `*_managed.xml` in the solution repos (all environments available): shapes, order, and values, with counts. Search Microsoft's docs too, and record that nothing was found if so. Do not add a spec without this evidence.
2. **Write the spec** as `Models/ControlDefaults/<Control>Defaults.cs`, copying `ModelFormControlDefaults.cs`: `ControlName`, `Evidence` (the survey counts, sources, and exceptions), `Parameters` (top-level defaults, with attributes for typed ones), `Blocks` (nested elements with children defaults and Dataverse's order), `ParameterOrder`.
3. **Register it** in `ControlDefaultsRegistry.All`. Unregistered controls keep every parameter verbatim.
4. **Test it** against a verbatim real `<parameters>` sample: export omits the defaults, build reproduces the sample byte-for-byte, and a non-default value survives. See the `ModelFormControl_*` tests in `FormXmlWriterTests`.
5. **Mention exceptions** (instances that lack a default) in `Evidence` and in `docs/yaml-conventions.md`.

Logic lives in `ControlDefaultsApplier` (`Strip` for export, `Restore` for build); keep those two exact inverses.
